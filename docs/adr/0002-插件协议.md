# ADR-0002 · 插件协议（一切皆插件）

- **状态**：已接受（冻结 · 全项目宪法）
- **日期**：2026-09-15
- **依据**：任务书总纲 §1.3（修订 1 由"模块协议"升级而来）
- **影响范围**：全项目，尤其 T14（框架）与 T05–T12（全部业务插件）

---

> **注（2026-10-19）**：项目已定名 **Alongside**（中文「在你身边」），定位为 **AI 人生协助系统**。本文是决策当时的原始记录，其中「人生管理系统 / life-os」等表述为当时的用词，保留不改。

## 背景

人生管理系统的功能注定会长。今天要日程表、待办、笔记、理财、复盘、习惯，
明年可能想加"课程表""体检记录""读书进度"。

如果每加一个功能就去改一次主干代码，这个系统一年内就会变成**没人敢动的泥球**。
而主人要的是一个**能用四年的安静的大后方**。

所以问题不是"怎么做功能"，而是：**怎么让功能可以无限地加起来，而主干永远不动。**

---

## 决策

### 设计理念：一切皆插件

> **内核只提供框架，能力全部由插件长出来。**
>
> 内核只负责七件事：**窗口 / 路由 / 鉴权 / 事件 / 数据 / 设置 / 扩展点**。
> 内核**不认识任何业务** —— 它不知道什么叫"日程""待办""理财""习惯"。
> 所有业务能力都以插件形式存在：现在这 9 个是插件，未来任何一个新想法也是插件。

### 唯一的判据

> ### 能不能在不改内核一行代码的前提下，加一个新插件？

如果为了一件新事情必须去动 `kernel/` 或 `core/` ——
**那是框架的 bug，不是需求的问题。** 先修框架，别急着加功能。

---

## 插件清单 `manifest.json`

每个插件必须自带一份：前端靠它注册窗口与扩展点，后端靠它挂路由，AI 靠它发现能力。

```json
{
  "id": "calendar",
  "name": "日程表",
  "version": "0.1.0",
  "kind": "builtin",
  "minKernel": "0.1.0",
  "kernelApi": "^1",
  "icon": "cal",
  "description": "横轴天、纵轴小时的可嵌套日程",
  "author": "yunxi",
  "window": { "w": 960, "h": 620, "minW": 520, "minH": 380, "singleton": false },
  "entry": "@apps/calendar",
  "api": {
    "base": "/api/v1/calendar",
    "openapi": "/api/v1/calendar/openapi.json",
    "health": "/api/v1/calendar/health"
  },
  "provides": ["calendar.event.read", "calendar.event.write", "calendar.slot.free"],
  "requires": ["notes.note.read"],
  "slots": ["desktop.dock", "dashboard.card", "settings.page", "ai.tool"],
  "emits": ["calendar.event.created", "calendar.event.updated", "calendar.event.deleted"],
  "consumes": ["notes.note.saved"],
  "permissions": ["db:own", "bridge:read"],
  "migrations": "api/migrations",
  "settingsSchema": "api/settings.schema.json",
  "lifecycle": { "onInstall": null, "onEnable": null, "onDisable": null, "onUninstall": null }
}
```

| 字段 | 含义 | 为什么重要 |
|:--|:--|:--|
| `kind` | `core` / `builtin` / `third-party` | 决定能不能被卸载、从哪加载 |
| `kernelApi` | 要求的**内核接口版本**（如 `^1`） | 内核升级后老插件必须能被识别为不兼容，而不是静默崩 |
| `provides` / `requires` | 声明"我提供什么能力 / 我需要什么能力" | **这就是权限系统的基础。** `requires` 没写的能力，插件调不通 |
| `slots` | 我要往哪些**扩展点**上挂东西 | 决定这个插件能"长"在系统哪些位置 |
| `permissions` | `db:own` / `db:read:<id>` / `bridge:read` / `net:out` / `fs:plugin` | 内核据此授权，越权直接拒 |
| `migrations` | 自己的迁移目录 | 插件自带表结构，内核负责按序执行 |

## 三类插件

| 类型 | 从哪来 | 能否禁用 | 能否卸载 | 例子 |
|:--|:--|:--:|:--:|:--|
| `core` | 内核自带 | 否 | 否 | `auth`（只有一个） |
| `builtin` | 随系统发布 | 是 | 否 | T05–T12 的全部 |
| `third-party` | 用户装 zip / 丢文件夹进 `plugins/` | 是 | 是 | 未来任何新想法 |

**三种都必须能被禁用**（除了 core），**禁用后系统必须完好运行** —— 这是框架是否合格的试金石。

## 扩展点清单（slots）

| 扩展点 | 插件可以长到哪 | 例子 |
|:--|:--|:--|
| `desktop.dock` | 桌面坞上加图标 | 所有带窗口的插件 |
| `desktop.widget` | 桌面挂件 | 时钟、倒计时、今日进度环 |
| `dashboard.card` | 概览页加一张卡 | 理财快照、习惯连续天数 |
| `topbar.action` | 顶栏加按钮 | 番茄钟、专注模式开关 |
| `calendar.block.renderer` | 自定义日程块的渲染 | 课程表插件、倒班表插件 |
| `calendar.overlay` | 在时间网格上叠加图层 | 天气、月相、考试周标记 |
| `inspector.panel` | 侧栏加面板 | 相关笔记、相关待办 |
| `settings.page` | 设置里加一页 | 每个插件自己的配置 |
| `search.provider` | 全局搜索接入自己的数据源 | 笔记、待办、日程、书签 |
| `ai.tool` | 把自己的能力注册成 AI 可调用的工具 | **这是"AI+"的正门** |
| `notification.channel` | 增加一个通知通道 | 邮件、Telegram、Server酱 |
| `command.palette` | 注册命令 | 任何可被快捷执行的动作 |

**这张表是可以长大的。** 新增扩展点是内核允许的事（属于正常演进），
但**第三方插件不许自己新增扩展点** —— 扩展点是内核资产，走 RFC 增补。

## 硬规则（违反任一条，插件将无法与其他插件共存，或被内核拒绝加载）

| # | 规则 |
|:--:|:--|
| 1 | `id` 全局唯一，小写英文，等于 URL 前缀、等于目录名 |
| 2 | 插件之间**不许直接 import**，只能通过 ① 事件总线 ② 对方公开的 API ③ 扩展点 |
| 3 | 插件**不许自己写死颜色**，只能用 `--accent` 等设计令牌 |
| 4 | 插件**不许自己写登录**，鉴权由内核统一注入 `Authorization: Bearer <jwt>` |
| 5 | `manifest.json` 是契约，改它等于改接口，要走 RFC 流程 |
| 6 | ★ **内核里不许出现业务词汇**（`kernel/` 与 `core/` 下不得出现 calendar/todo/notes/finance/habit）—— 这是理念**唯一可机器验证的判据** |
| 7 | ★ **能力必须声明**：读别的插件数据必须在 `requires` 写明，没写的调用内核直接拒 |
| 8 | ★ **数据库隔离**：每个插件只写自己的表（表名以插件 id 为前缀）；跨插件读数据走 API，不许 join 别人的表 |
| 9 | ★ **可被禁用**：任何插件被禁用后系统必须优雅降级、不许白屏；依赖方降级为"该能力不可用" |
| 10 | ★ **卸载干净**：`third-party` 卸载后表、文件、扩展点注册、事件订阅、定时任务全部清理 |
| 11 | ★ **版本可判**：内核与插件都声明版本；不兼容时**明确拒绝加载并给出人话原因**，不许静默失败 |
| 12 | ★ **热插拔目标（v0.2）**：装/卸/启用/禁用不需要重启服务。v0.1 允许重启，但架构上必须留好位置（注册表与状态分离） |

## 备选方案与否决理由

| 被否决的方案 | 否决理由 |
|:--|:--|
| **单体应用，功能直接写在主干** | 一年内变成泥球；加一个功能要动十处 |
| **只做"模块化"（代码分目录但不隔离）** | 目录只是目录，改不掉"互相 import、共用表、共用状态"的纠缠 |
| **允许第三方插件自建扩展点** | 扩展点会碎片化，最终谁也说不清系统有哪些挂载位 |
| **v0.1 就做真沙箱（限文件/网络）** | 单人系统、自己写的插件，收益不抵成本。改为**声明式权限**（越权拒） |
| **v0.1 就做"从 URL 一键装插件"（应用商店）** | 涉及代码信任与签名，风险与工作量都不小，留 v0.3 |
| **让插件直接共享数据库连接、互相 join** | 表结构变成事实上的公共契约，改一处崩一片 |

## 后果

### 正面

- **新增能力 = 加一个目录**，主干零改动。这是本项目最重要的可演进性。
- 每个插件可独立开发、独立测试、独立禁用 → **13 个 agent 可以并行且不打架**。
- 插件被禁用后系统仍可用 → 任何一个模块写坏了，不会拖垮整个系统。

### 负面 / 需要接受的代价

- **多一层间接**：读别的插件的数据要走 HTTP，比直接函数调用慢（单用户场景可忽略）。
- **框架必须先做**：T14 是硬闸门，它不交付，8 个业务插件就不能开工（见 `分发索引.md` 第 3 批）。
- **对执行者的纪律要求高**：不许碰内核、不许 import、不许写死颜色、不许 join 别人的表
  —— 这四条会被反复违反，所以做成了可机器验证的检查。

### 落实手段

| 手段 | 在哪 |
|:--|:--|
| `check_kernel_purity.py` | T14 交付，`make lint` 里执行，内核洁癖可机器验证 |
| `create_plugin.py` | T14 交付，**新插件唯一入口**，防止各卡自创写法 |
| `plugin.schema.json` | T14 交付，manifest 校验 |
| 验收三问 | 每张插件卡交付前自问：禁用后系统还好吗 / 碰内核了吗 / 挂的插槽和 manifest 一致吗 |
