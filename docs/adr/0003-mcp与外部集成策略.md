# ADR-0003 · MCP 与外部集成策略

- **状态**：已采纳（2026-09-18）
- **决策者**：主人 + 云昔
- **影响范围**：所有与外部系统交互的插件（T08 理财 / T09 复盘 / 未来的 AI 能力）、内核的对外能力暴露方式
- **相关**：ADR-0002（插件协议）、`contracts/plugin.schema.json`

---

> **注（2026-10-19）**：项目已定名 **Alongside**（中文「在你身边」），定位为 **AI 人生协助系统**。本文是决策当时的原始记录，其中「人生管理系统 / life-os」等表述为当时的用词，保留不改。

## 1. 背景

主人提出：财务模块要与云服务器上的 **BeeCount Cloud** 联动、复盘模块要与本机 **Work-Review** 联动，
并问了一个关键问题：

> 「BeeCount 支持 MCP 调用，我们的人生管理系统需不需要兼容一下 MCP 调用？还是继续走 API 调用？」

调研后发现，两个外部项目**各自都同时提供 REST 与 MCP**：

| 项目 | REST | MCP | 部署位置 |
|:--|:--|:--|:--|
| BeeCount Cloud | ✅ 完整 OpenAPI（`/docs`） | ✅ 内置 server，PAT 鉴权（`/api/v1/profile/pats`） | **云服务器**（单 Docker 容器，8869→8080） |
| Work-Review | ✅ Localhost API（`127.0.0.1:47831`，Bearer Token） | ✅ stdio server | **主人本机**（Tauri/Rust 桌面程序） |

所以问题不是"选哪个协议"，而是"**什么场景该用哪个**"。

## 2. 决策

### 2.1 ★ 核心：REST 与 MCP 分层，不是二选一

> **REST/API 是「给程序用的接口」，MCP 是「给 AI 用的接口」。它们服务不同的消费者。**

| 调用方 | 协议 | 理由 |
|:--|:--|:--|
| 前端 ↔ Alongside 内核 | **REST** | 确定、可测、有 OpenAPI、幂等、可缓存 |
| 插件 ↔ 插件 | **REST + 事件总线** | 同上；且插件之间不许直接 import（ADR-0002 硬规则） |
| **Alongside → BeeCount** | ★ **MCP**（2026-09-18 实测修正，见 §2.6） | 它的 PAT **只能**用于 MCP 端点；走 REST 得拿主密码换 JWT |
| **Alongside → Work-Review** | **REST**（本机 API，经桥转发） | 它有 20+ 现成端点，含日报导出 |
| **AI 客户端（Claude / Cursor 等）→ Alongside** | ★ **MCP** | 这是"AI 协助写日记/检索/整理"的正门 |

**Decision 1**：Alongside 内部一切照旧走 REST；**不依赖**外部系统的 MCP 实现
（它们改 MCP 不影响我们）。Alongside 自己**要做的是一个 MCP server**——对外暴露能力，而非对内替代 REST。

### 2.2 MCP 不需要"预留端口"，需要"能力可声明"

`manifest.provides` 已经是能力声明（ADR-0002）。**MCP 工具就是它的映射**：

```
插件 manifest.provides        →   MCP tool
────────────────────────────────────────────────
calendar.event.write          →   create_event / update_event / delete_event
todo.item.write               →   create_todo / toggle_todo
notes.note.write（→ 文档树）   →   write_document
notes.note.read               →   read_document / search_documents
finance.snapshot.read         →   get_finance_snapshot
review.daily.read             →   get_daily_review
```

**Decision 2**：新增一个**内置插件 `mcp`**（不是内核模块），它读取各插件的 `provides`，
把它们映射成 MCP tools。

**判据（可机器验证）**：给 AI 加一个新工具，**只需插件的 manifest 里多一行 `provides`**，
不改内核、不改 mcp 插件。做不到就是设计错了。

### 2.3 鉴权：AI 不能拿主人的登录令牌

MCP server 面向 AI 客户端，必须用**独立的、可吊销的、可限定范围的凭证**：

- 沿用 BeeCount 的既有做法：**PAT（Personal Access Token）**；
- 存放在 `app_setting`（T04 已建）或独立表，**只存哈希**；
- 每个 PAT 限定 `scopes`（如 `doc:read` / `doc:write`），越权直接拒；
- 支持随时吊销；**所有经 MCP 的写操作都进 `audit_log`**（T04 已建）——AI 改了什么必须可追溯。

**Decision 3**：MCP 用 PAT，不用 JWT 登录令牌；写操作全部留审计。

### 2.4 云 ↔ 本机：方向必须是"本机主动连云"

网站在云服务器上，而 Work-Review / Obsidian / Windows 通知都在本机。
**云服务器不能主动连本机**（家庭宽带无公网 IP）。

**Decision 4**：`services/bridge/`（T07 已建成 865 行）从"笔记同步专用"**升级为通用本机代理**：

```
本机 bridge  ──主动连云（WS）──►  Alongside 云端
   │                                  │
   ├─ 持有 Work-Review 的 token        ├─ 有提醒 → 推给 bridge → 弹 Windows 原生通知
   └─ 能调 127.0.0.1:47831            └─ 要日报 → 让 bridge 去调 Work-Review API
```

三条硬要求（总纲雷区 #9 的具体化）：
1. **心跳 + 指数退避重连**，断线自愈；
2. 前端必须明确显示「桥离线」，**不许一直转圈**；
3. 桥只做**被动的代理执行**，不做业务判断（业务逻辑留在云端插件）。

### 2.5 性能与信息密度：横切契约，不是某个插件的功能

**Decision 5**：把下列要求写进**模板包与所有前端卡的验收清单**（否则各写各的，拼起来还是慢）：

| 手段 | 用在哪 |
|:--|:--|
| 虚拟化长列表 | 日程时间轴、待办、笔记列表、交易流水 |
| 乐观更新 | 所有写操作（勾选、拖动） |
| SSE 而非轮询 | 桥状态、同步状态、提醒 |
| CSS transform/opacity 动画 | 窗口拖动、坞动画 |
| 骨架屏 + 悬停预取 | 窗口打开、页面切换 |
| 信息密度：网格 + 紧凑卡片 + 可折叠 | "一口气展示最多信息" |
| 首屏体积预算（gzip 后 < 250KB） | 验收清单 |

### 2.6 ★ 实测修正（2026-09-18）：对 BeeCount **必须走 MCP**

本文初稿写的是「Alongside 调外部一律走 REST，不依赖它们的 MCP」。**实测推翻了这条**：

```text
GET /api/v1/read/ledgers   with  Authorization: Bearer bcmcp_...
→ HTTP 403 {"message":"PAT can only be used for MCP endpoints"}
```

**BeeCount 的 PAT（`bcmcp_*`，scopes `mcp:read` + `mcp:write`）只能访问 MCP 端点，打不了普通 REST API。**

于是接它的机器通道只剩两条：

| 方案 | 评价 |
|:--|:--|
| ★ **A. 走 MCP**（用现成 PAT） | **采纳**。令牌已限范围、可吊销、可审计 |
| B. 走 REST（用登录密码换 JWT） | 否决。要在 Alongside 里存主人**主密码**，或维护 refresh token 链，风险显著更高 |

**而且走 MCP 并不比 REST 差**（`/app/src/_mcp_internal_client.py` 注释原文）：

> MCP write tools 走 HTTP self-call 到 `/api/v1/write/*`，这样能完整复用 FastAPI dep tree、
> **idempotency**、**sync_change 登记**、**WebSocket 推送**等逻辑，跟 web / mobile 走完全相同的代码路径。

**即：走它的 MCP 写账 ≡ 走它的 REST 写账**（同一条代码路径、同样的保证）。
MCP 不是二等公民，它是 BeeCount 官方给机器用的正式接口。

**决策 1 修正为**：Alongside 内部仍走 REST；**调 BeeCount 走它的 MCP**；
调 Work-Review 走它的 Localhost REST（它没有 MCP-only 限制）；
Alongside 自己**同时**对外暴露 MCP（给 AI）与 REST（给程序）。

**实测细节**（端点、18 个工具、鉴权、服务器信息）见
`E:\ai work\workbuddy\outputs\人生管理系统\对接档案-外部系统实测.md`。

### 2.7 ★★ 实测修正（2026-09-18 晚）：传输通道用 **frp**，不用自建 bridge

§2.4 决策 4 原本写的是「把 `services/bridge/` 升级为通用本机代理」。**复查后修正。**

**排查实测结论**（主人本机 + 云服务器全查过）：

| 检查 | 结果 |
|:--|:--|
| cloudflared / Tailscale / frpc / ngrok / ZeroTier | ❌ 全都没有 |
| `~/.ssh/pocket_bridge/` | 有（7-06 创建，注释 `pocket_bridge@yunxi`），但**公钥从未部署到云** → 开了头没做完 |
| **云服务器上的 frps** | ✅ **已安装**，9-16 软关停，**恢复路径保留**：`systemctl enable --now frps` |
| WSL → Windows `49996` | ✗ 不通（防火墙未放行）—— **再次证明通道必须建在 Windows 侧** |

**决策**：

1. **正式方案：云上 frps + Windows 跑 frpc**。理由：
   - **frps 已在云上**（基础设施已就绪，总工作量最小）
   - **frpc 内置重连**，天然满足「心跳 + 指数退避」的要求；裸 `ssh -R` 没有，需另写守护
   - **多服务友好**：Work-Review（T09）、本机笔记服务（T07）、通知（T05）都能挂一份配置，而不是每个服务一条命令
2. **`ssh -R` 降级为「验证工具」**：先跑一次证明链路成立（云能碰到本机 49996），再落 frp。
3. ★ **`services/bridge/` 重新定位**：它**不再承担传输**（那是 frp 的活），
   但**它里面 Obsidian 相关的业务逻辑（watcher / scanner / reader）仍然需要**——
   因为 Obsidian 是**文件系统**不是端口，frp 转不了。
   新形态：**桥退化成一个"只读的本机文件服务"**，由 frp 把它暴露给云端。
   → **传输归 frp，业务归各本机小程序**，两者不要混在一起。

**对卡的影响**：
- **T09**：`WORK_REVIEW_BASE_URL` 的"经桥"取值从 `/proxy/work-review` 简化为
  **`http://127.0.0.1:<frp 在云上映射的端口>`**（frp 是原样 TCP 转发，不需要代理路径约定）
- **T07 / T05**：改为对接 frp，不再依赖自建 bridge 做传输

## 3. 后果

**正面**
- 三种消费者（前端 / 插件 / AI）各得其所，互不干扰；
- 新增 AI 能力**不改内核**（只加 `provides`）——与 ADR-0002 的判据一致；
- 外部系统换实现（REST→MCP 或反之）**不影响** Alongside；
- 桥一次建成，后续所有"云要碰本机"的需求全部复用。

**代价 / 风险**
- 需要维护一层 `provides → tools` 映射（但它是声明式的、极薄）；
- PAT 的签发/吊销/审计是一套新东西，必须做对（否则 AI 有越权风险）；
- 桥是本机常驻进程 → **需要主人同意**（见 §4 待确认）。
