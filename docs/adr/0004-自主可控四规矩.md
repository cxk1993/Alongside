# ADR-0004 · 自主可控四规矩（对外依赖的纪律）

- **状态**：已采纳（2026-09-19，X02 横切契约落地）
- **决策者**：主人（拍板）+ 云昔/Zcode（成文）
- **影响范围**：所有与外部系统交互的代码（现有：BeeCount 联动、Work-Review 接入、本机桥；未来：PWA 推送、通用本机代理、任意 agent 接入），以及任何新增第三方依赖
- **相关**：ADR-0003（MCP 与外部集成策略）、`总纲-Alongside` §「自主可控四规矩」、全项目计划总表 §5 `X02`

---

## 1. 背景

主人的定位原话：**「不对别的项目高度依赖，但也不重复造轮子。」**

Alongside 已接入两个外部系统（BeeCount、Work-Review），未来还会接更多。外部系统会改版、会停服、会跑路——
而 Alongside 里存的是主人前半生的记录，**不能被任何外部项目绑架**。

ADR-0001/0002/0003 解决「怎么接」；本 ADR 解决「接的时候如何不失去自主」。
这不是新要求——是把项目已有实践**固化为纪律**，让后续每一张涉及外部交互的卡有据可依。

## 2. 四规矩（逐字执行）

### ① 外部只经「单一适配器文件」

- 与任一外部系统的**全部往来**（请求构造、鉴权、字段映射、重试）只允许存在于**一个**适配器文件里；
- 业务代码不许直接 import 外部 SDK、不许散落拼 URL——只调适配器暴露的抽象接口；
- **现行范例**：`services/api/modules/finance/beecount_mcp.py`（+ `beecount_sync.py`）是 BeeCount 的唯一通道；
  `modules/review` 的 upstream client 是 Work-Review 的唯一通道。

### ② 数据主权在自己

- 外部系统只是数据源或展示端；**权威副本永远落在 Alongside 自己的库**；
- 同步进来的数据先落本地表/快照（如 `finance_snapshot`），再给业务与前端用——外部挂了，本地数据与功能不塌；
- 例外说明：数据若由主人在外部系统原生产生（如 BeeCount 的记账行为本身），原始数据天然在外部——
  但 Alongside 侧必须保有可用的本地副本/快照，且对外只读不依赖回写。

### ③ 内部认抽象、不认品牌

- 内部代码不许出现「如果是 BeeCount 就……」式的品牌分支；只认 `上游/适配器` 抽象；
- **现行范例**：`FINANCE_UPSTREAM` / `REVIEW_UPSTREAM` 的 `mock/api` 配置切换就是此规矩的现行实现——
  换一个同类外部服务 = 换一个适配器实现 + 一行配置，业务层零改动。

### ④ 新依赖必过「三问」

引入任何新外部服务 / 第三方库之前，回答：

1. **没有它不行吗？**（标准库 / 已有依赖 / 少量自写代码能否先到 80 分？）
2. **出问题能看清吗？**（行为可审计、可降级、可 mock 吗？）
3. **它消失了疼多大？**（替换时若要改动很多处——**不许引入**；只许伤一处 = 适配器）

三问未全过 → 不引入；主人特批除外（例外必须记录在 §5）。

## 3. 现状对照（落地即核，不是口号）

| 规矩 | 已符合的现行实践 | 待办 / 持续动作 |
|:--|:--|:--|
| ① | beecount_mcp/sync 单文件；review upstream client 单文件 | 新增外部交互时自查「适配器唯一吗」 |
| ② | `finance_snapshot` 本地快照；BeeCount 只读不回写 | 金额映射拧紧时（解冻后）保持「本地权威」语义 |
| ③ | `FINANCE_UPSTREAM` / `REVIEW_UPSTREAM` 配置切换 | 无需脚本化，评审时口头纪律即可 |
| ④ | PWA 决策（不新增常驻进程、用标准 Web Push）即三问通过的范例 | 每次 `pyproject` / `package.json` 加依赖时过一遍三问 |

## 4. 后果

- **正面**：外部系统可替换、可降级；主人数据永不锁死于第三方；接新服务成本 ≈ 一个适配器文件。
- **代价**：适配器成为唯一改造点，接口设计要先行；少量「本来一行的 SDK 调用」要包一层。
- **执行**：本 ADR 即总表 X02 的落地物；后续涉及外部交互的卡，验收清单加一条「符合 ADR-0004」。
