# RFC-001 · 清掉契约描述里的内部协作代号

> **用途**：申请变更**已冻结的契约**。
> 冻结范围：`contracts/**`、任何 `manifest.json`、`docs/adr/**`、数据字典。
> **文件命名**：`RFC-001-简短标题.md`，编号递增。

- **提出者**：汐瑶
- **状态**：**implemented**（2026-10-10 主人批准并执行；`云昔` 一处经裁定保留）
- **日期**：2026-10-10
- **批准人**：主人

---

## 1. 动机

仓库已**转公开**（`github.com/cxk1993/Alongside`）。而 `contracts/` 是外部读者最先看的文件之一，
里面却留着一批**只对内部协作有意义**的代号：

- `plugin.schema.json` 的 4 处 `description` 里写着 `总监令 78`、`TX-DEG-01`、`TX-ACT-01` ——
  对开源读者是天书，且**不提供任何契约语义**（字段叫什么、什么类型、可不可省，文字里本来就有）。
- `contracts/README.md` 第 21 行「由主人（或云昔）批准」里的 **`云昔`** 是内部协作角色名。

这不是「这样更优雅」——它**已经造成了实际阅读障碍**：开源读者读 schema 时会困惑
「TX-DEG-01 是什么？我该去哪查？」。同时，这类内部流程信息外泄也非本意。

**前例**：本仓 2026-10-10 已有一次同类清理（`4c33796`，对外文档去内部黑话），
本次是把同一口径**补齐到契约目录**（当时因契约冻结而留待 RFC）。

## 2. 具体改什么

**只改 `description` 字符串里的文字 —— 零字段增删、零类型变化、零约束变化。**

```diff
- "description": "★ 路径 a（总监令 78）：仅 container 型可省 api；其余 kind 必须声明 api。"
+ "description": "★ 路径 a：仅 container 型可省 api；其余 kind 必须声明 api。"

- "description": "★ 路径 a（总监令 78）：容器型模块（kind=container）的页签声明。……"
+ "description": "★ 路径 a：容器型模块（kind=container）的页签声明。……"

- "description": "TX-DEG-01 软依赖：缺了不阻塞启动，O1 挂 degraded+reason_code。与 requires 互斥……"
+ "description": "软依赖：缺了不阻塞启动，O1 挂 degraded+reason_code。与 requires 互斥……"

- "description": "声明式激活事件（TX-ACT-01）。缺省或含 startup:always = 启动即激活……"
+ "description": "声明式激活事件。缺省或含 startup:always = 启动即激活……"
```

**★ 建议保留的一处**（请主人裁）：

`contracts/README.md:21` 的「由主人（或云昔）批准」—— 这里 `云昔` 是**流程里的真实角色**
（谁有权批准契约），删掉会丢失规则信息。**本 RFC 不动它**；若主人认为对外只应写「主人」，
请在批准时注明，我再单开一条改。

## 3. 影响面（必填，写全）

| 受影响的是谁 | 要改什么 | 工作量 |
|:--|:--|:--|
| 契约校验器（`core/plugins/validate.py`） | **无** —— 只读 `type`/`enum`/`required`/`properties` 等结构键，从不读 `description` | 无 |
| 后端各模块 | **无** | 无 |
| 前端 | **无** | 无 |
| 数据库 | **无** | 无 |

**数据迁移**：无（纯注释文字）。

**已实测**：全仓 `grep` 确认**项目代码零命中**读 `description` 做逻辑判断
（唯一命中都在 `services/api/.venv/` 的第三方库 fastapi / packaging 里，与本项目无关）；
契约校验器 `core/plugins/validate.py` 只读 `type`/`enum`/`required` 等结构键。

## 4. 迁移方案

一步到位（纯文字替换，无阶段、无回滚风险）。改完重跑
`services/api/tests/test_plugins.py`（schema 校验相关）确认全绿即可。

## 5. 不改会怎样

- 开源读者读契约时撞上天书代号，且**无处可查**（那些代号不在仓库任何地方有解释）。
- 内部流程信息持续对外暴露。
- 成本：0（改的是注释文字，不动任何结构）。

## 6. 批准与执行

1. 由主人批准。
2. 按契约流程，**由契约所有者统一改** —— `plugin.schema.json` 归 T14，
   本次由汐瑶代执行（主人已在 2026-10-10 原则同意「清非契约部分之外的契约内代号」）。
3. 执行后状态改为 `implemented`，验证证据：schema 校验测试全绿 + 仓库 `grep` 代号归零。

---

> **绕过的代价**：任何一个卡自己改了契约，其他 12 张卡就都建立在一个不存在的事实上了。
> 这类问题发现得越晚，返工越大。
> —— 本 RFC 正是为了**不绕过**这条规矩而写。
